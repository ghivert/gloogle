# Gloogle

Gloogle is a search engine, able to query the entirety of the Gleam ecosystem!
Search for a function or a type, and let the magic happen!

[First beta version is available!](https://gloogle.run)

## Features

Some features are already implemented, and some others are still on the roadmap!

- Search for a function or a type by its name
- Search for a function or a type by its type
- Search with a document search accross the gleam ecosystem (with vector search)
- Navigate in the documentation by clicking on types
- Head back to [HexDocs](https://hexdocs.pm) when looking for something specific
- Find a way to expose the database
- Get GitHub stars for each package on a regular basis
- Enables Search in documentation directly
- Filters included with `in:module`, `in:name`, `in:signature` and
  `in:documentation`

## Future developments

## Getting Started

The backend (`apps/jupiter`) needs a Postgres database and an S3-compatible
bucket for the package-archive cache. Both run locally with Docker:

```sh
# Postgres on localhost:25432, RustFS (S3) on localhost:29000 (console on 29001).
# Deliberately far from the defaults so nothing collides with other local stacks.
docker compose -f infra/local/compose.yml up -d
```

Point jupiter at them from `apps/jupiter/.mise.local.toml` (gitignored, read by
`mise` as environment variables):

```toml
[env]
PORT = 3000
LOG_LEVEL = "DEBUG"

# Local stack (infra/local/compose.yml).
DATABASE_URL = "postgres://gloogle:gloogle@localhost:25432/gloogle?sslmode=disable"
BUCKET_URI = "http://localhost:29000/gloogle"   # full URL = path-style local S3
SCALEWAY_ACCESS_KEY = "gloogle"                # RustFS credentials from the compose file
SCALEWAY_SECRET_KEY = "gloogle-local"

# Used to access hex API.
HEX_API_KEY = "xxxxx"

# Used to crawl stargazers.
GITHUB_TOKEN = "xxxxx"
```

In production `BUCKET_URI` is the bare virtual-hosted Scaleway host
(`hex-mirror.s3.fr-par.scw.cloud`) and the keys are the Scaleway ones; the S3
client picks the shape from the variable.

### Seeding the local stack from production

Part of the data cannot be regenerated by re-running ingestion: the `hex_read`
cursors, `analytics`, `analytics_timeseries`, `search_analytics` and the GitHub
popularity history only exist in production. `infra/local/scripts/seed-local.sh`
copies everything:

```sh
# 1. Database: pg_dump from the production Postgres (Render), restore locally,
#    then dbmate up for migrations newer than production.
# 2. Bucket: mirror the Scaleway bucket to infra/local/dumps/, then into RustFS.
PROD_DATABASE_URL="postgres://…render…/gloogle?sslmode=require" \
  infra/local/scripts/seed-local.sh        # or: seed-local.sh db / seed-local.sh s3
```

The bucket half reads `BUCKET_URI`, `SCALEWAY_ACCESS_KEY` and
`SCALEWAY_SECRET_KEY` from the environment (`mise env` in `apps/jupiter`
exports them). Dumps and the bucket mirror land in `infra/local/dumps/`
(gitignored) so a reseed does not hit production twice.
